## 邮箱验证码：发送按钮 + 60 秒倒计时

需求：验证码虽然是示意（固定 123456），但要有「发送验证码」按钮和 60 秒倒计时。

> ⚠️ 用户原话是「手机验证码」，但项目里**完全没有手机号概念**（grep 过 src/docs/static/scripts，
> 零命中），只有上一轮做的邮箱验证码。按上下文理解为给邮箱验证码加发送流程。
> 若真要手机号字段是另一件事（迁移 + 表单 + 文档全改），需要用户确认。

### 核心设计决定：冷却由服务端裁决，客户端只做镜像
浏览器自己数的倒计时**刷新就没了**。所以：
- `codeRequests: Map<email, epochSeconds>` 记每个地址上次发送时间（进程内，注释说明了将来要落库）
- `POST /register/email-code` → 发送 + 返回剩余秒数
- `GET /register/email-code?email=` → **只读**剩余秒数，不产生副作用
- 前端 `useCooldown()` 用**墙上时钟**（`endsAtRef = Date.now() + n*1000`，250ms tick 重算）
  而不是递减计数 —— 后台标签页被节流时不会漂移
- 刷新后靠 **sessionStorage** 里的 `skillhub.register.lastEmail` 找回是哪个地址，
  再向服务端问剩余时间（用 session 不是 local：等待很短，新标签页就是新一次尝试）

### ⚠️ 踩过的三个真 bug（都是设计缺陷，不是打字错误）

**1. 「查看剩余时间」和「发送」混成一个接口**
最初 GET/POST 都调 `requestEmailCode`，而它会**打开**冷却窗口。结果：用户只是在输入框里
敲邮箱，onChange 触发的查询就把唯一一次发送机会用掉了 —— 点「发送」时拿到非 0，
显示成"还在冷却"而不发。**拆分**：`emailCodeStatus()` 只读、`requestEmailCode()` 才开窗口。

**2. 返回 0 的语义反了**
最初成功发送时返回 `cooldownSeconds: 0`（想表达"现在可用"），而前端 `start(0)` 是"清零"分支，
于是点了发送倒计时根本不启动。改成：**成功发送返回完整 60**，且响应加 `sent: boolean`，
前端只看 `sent` 决定要不要提示"已发送"，不再靠数字猜。

**3. `askedForRef` 让"换回原地址"恢复不了冷却**
原本用"是否已查过这个地址"去重。但 `agent-browser type` 逐字符输入会经过中间态，
`sunli@` 这种半截值可能已被标记，导致换回完整地址时判为"已查过"而跳过查询。
改成跟**当前屏幕上反映的地址**比（`matchesRef`），而不是"上次查过的地址"。

### 其他要点
- 路由 `src/routes/register.email-code.ts` 同时挂 GET + POST。
  **一个 page route 只能有一个 method per path**，`/register` 已被页面 GET + 提交 POST 占满，
  所以另开路径。
- 冷却**按地址**而非全局；邮箱大小写不敏感（与存储一致）。
- 邮箱改动会清空已填验证码 + 确认提示 —— 收件人变了旧的就不作数。
- 按钮固定 `min-width: 106px`，60→9 跳数不抖布局；移动端 `.code-row` 换行（各占 100%）。
- 「验证码已发送」用 `.field-hint-ok`（accent 色），与错误提示同一位置但不同色。
- `useCooldown()` **不要传秒数参数** —— 时长由服务端给，hook 只镜像。
  `start`/`clear` 用 `useCallback([])` 保持引用稳定，否则调用方的 `useCallback` 每次渲染都重建。

## 管理端：待审核行默认展开注册资料

需求：「admin 用户管理也要展示这些新加的字段」。

**先查了 —— 功能上一轮已经做完了**：`ProfileDetail` 组件 + 「查看资料」折叠行，7 个字段都在。
问题是**默认收起**，审核人看不到。用户选的方案：**保留折叠，但待审核行默认展开**。

### 改动（`src/routes/admin.users.tsx`）
- `expanded: string | null` → **`detailOverride: Record<string, boolean>`**。
  只记**例外**：默认值是 `item.status === 'pending'`，手动点过才写进 override。
  （用 `expanded` 单值记不住「默认展开」——待审核行会被记成 closed。）
  判据：`detailOverride[item.id] ?? item.status === 'pending'`
- `map()` 改成 `map(item => { const showDetail = ...; return <Fragment>... })` 加了 return。
- **配套必须做**：review `onSuccess` 里 `setDetailOverride` 补一条 `id: true`。
  否则审核通过瞬间状态从 pending 变 approved，**正在看的资料会突然消失** ——
  审核人正在读就丢了。这个 bug 只有真点一次「通过」才看得到。
- 纯前端展示逻辑，**服务端契约没变 ⇒ 冒烟不用新增用例**（317 断言不变）。

### 验证
浏览器造 3 个待审核账号（孙琪/淡马锡/新加坡、陈伟/JPMorgan/美国、李静/汇丰/中国香港）：
- 待审核标签页：3 个 profile 面板全部默认展开，内置 admin（已通过）仍收起 ✅
- 字段齐全：姓名、邮箱、国家/地区、机构、岗位、办公地区、关注市场（标签）、研究需求 ✅
- 点「通过」后资料**仍保持展开** ✅（这条专门验证 onSuccess 的补偿逻辑）
- 中英文文案都对（「收起资料」/「Hide details」）✅
