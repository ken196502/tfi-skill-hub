## 写 Combobox 类组件的两个必踩坑（这次都撞了）
1. **Escape 必须用 `document.addEventListener('keydown', h, true)` 捕获阶段 + `stopPropagation()`**。
   `Modal` 组件在 `document` 上监听 keydown 关闭弹窗，而**它挂载更早 ⇒ 同为 document 上的监听器它先跑**，
   在 React `onKeyDown` 里 `stopPropagation()` 来不及（都在冒泡阶段，且 document 上按注册顺序），
   结果「在下拉里按 Esc 把整个弹窗关了」。捕获阶段先于任何冒泡监听，与注册顺序无关。
   TS 注意：React 的 `KeyboardEvent<T>` 遮蔽了 DOM 版，document 监听器要写 `globalThis.KeyboardEvent`。
2. **`openList()` 里要 `inputRef.current?.select()`**。否则有值的框聚焦后直接打字是**追加**成 `researchRisk Ops`
   而不是替换。注册页国家字段同样受益。
   另：截图里看到的"下拉被下方原生 `<select>` 盖住"是过渡动画中间帧，`elementFromPoint` 实测无重叠，勿误判。

## 瘦身：去掉「公开/私有」+「审核技能」，插件类别整体删除（2026-10-13 下半天）
用户要求：技能的操作只剩**发布、编辑、上下架**三项。公开私有与审核技能全部去掉（API + UI），
**插件（plugins）这个类别整个删掉**。数据库按约定直接重置。

### 关键发现：原本「公开私有」和「上下架」是同一套代码
`skills.visibility`（public/private）在管理端 UI 上被直接翻译成「已上架/已下架」——一列兼两职。
`moderation_status`（approved/pending_review/rejected）是独立字段，`reviewSkill` 实际就是在改 visibility。
所以「删公开私有但留上下架」必须先改数据模型，不能只删接口。

### 数据模型（迁移 v13）
- `skills.visibility` → **`skills.listing`**，值域 `listed` / `unlisted`；删 `moderation_status`。
- `namespaces.default_visibility` → `default_listing`（个人命名空间默认 `unlisted`）。
- **SQLite 改 CHECK 约束的可行做法（本机 3.51.2 实测）**：`ALTER TABLE ADD COLUMN 新列(带新CHECK)`
  → `UPDATE` 平移 → `ALTER TABLE DROP COLUMN 旧列`。**不需要重建表**，FK 与子表数据全保留。
  之前担心的「必须重建 skills 表」是多余的。
- FTS5 虚表**不能 ALTER**，只能 DROP + 重建 + 用 `INSERT...SELECT` 从源表重灌（38 条全回）。
- 迁移里写了 `DROP TABLE IF EXISTS plugin_version_files/plugin_versions/plugins`。
- **迁移保持 append-only**：v1 里的 plugins 建表语句**原样留着**（只加注释说明 v13 会删），
  这样老库从任意版本都能升上来。别为了「干净」去改历史迁移。

### 接口变更
- 删：`POST .../review`（×2）、`POST .../visibility`（×2）、`POST .../request-public`（×2）、
  全部 20 条 plugin 路由、3 个 admin plugin handler。
- 改：`POST /admin/skills/:slug/visibility` → **`POST /admin/skills/:slug/listing`**，body `{listing}`。
  `GET /admin/skills?visibility=` → **`?listing=`**。
- 发布/agent 发布的表单字段 `visibility` → **`listing`**（multipart 字段名也改了）。
- **K_MODERATE scope 保留**（还管 yank/deprecate/transfer/features），只是语义变成「上下架与版本标记」。
  审计动作 `review_skill_*`/`set_skill_visibility` → **`list_skill` / `unlist_skill`**。

### 连带清理
- 删 `repo/plugins.ts`(471) + `services/plugins.ts`(487) + `shared.ts` 的 canViewPlugin/
  resolvePluginRef/authorizePluginWrite/reindexPlugin/reindexAll 里的插件循环 + `manage.ts` 三个插件方法。
- **`content.ts` 的 `computeFingerprint` 随之变成死代码**（唯一调用点在 plugins），已删。
  反过来 `createZip`/`contentTypeFor`/`readMultipart`/`semver` 都有技能侧调用者，**都保留**。
- `platformStats` 与 `/metrics` 去掉 `plugins` 计数与 `skillhub_plugins_total`。
- FTS 搜索的 `docType` 列保留但恒为 `skill`（在响应契约里），search.tsx 的 `docType!=='plugin'` 过滤删除。

## v13 迁移脚本的生产级修正（2026-10-13 傍晚）
用户要去生产 VPS 做 docker 部署，要求「确保迁移脚本正确」。**之前只用本地库验证是不够的**——
本地库 38 条全是内置种子技能、0 条插件、0 条软删、0 条可疑标记，四类边界一个都不覆盖。
于是造了带真实边界数据的 v12 夹具重测，**查出 3 个真实缺陷**（都只会在生产暴露）：

1. **`DROP TABLE plugins` 是无条件执行的** —— 生产有插件数据就会静默销毁。
   改成**数据守卫**：建 `_skillhub_migrate_guard(must_be_zero INTEGER CHECK(must_be_zero=0))`，
   `INSERT ... SELECT 三张插件表的 COUNT(*) 之和`，非 0 就违反 CHECK → 事务回滚 → 库停在 v12 原样不动。
   这是**纯 SQL 里唯一能主动中止迁移的办法**（RAISE() 只能在 trigger 里用）。
   实测有插件时：报错 `CHECK constraint failed: must_be_zero = 0`，6 条断言全过（插件数据/旧列/技能/评论收藏评分均无损）。
2. **FTS 重建把 `is_suspicious` 和时间戳写死成 0** —— 被标记的技能在索引里丢失标记；
   `updated_at/created_at` 归零会让「按更新时间排序」的搜索结果变成任意顺序。
   改为 `s.is_suspicious` 与 `CAST((julianday(s.updated_at) - 2440587.5) * 86400000 AS INTEGER)`
   （julianday 能直接解析带 T/毫秒/Z 的 ISO-8601，实测与 `Date.parse` 完全一致，误差 1ms 内）。
3. **软删技能被 `WHERE soft_deleted_at IS NULL` 整条丢掉** —— 而 `reindexSkill` 是**保留并标记**
   `is_deleted=1` 的，搜索靠该列过滤。丢掉会让 `is_deleted` 恒为 0、该列失去意义。
   改为不写 WHERE、改用 `CASE WHEN s.soft_deleted_at IS NULL THEN 0 ELSE 1 END`。

### 两个必须记住的坑
- ⚠️ **模板字面量里的 SQL 注释不能带反引号**：`` `-- `reindexSkill` 会 `` 里的反引号会**提前终止模板字符串**，
  表现为 schema.ts 报 TS1005 + 服务启动崩溃，但报错位置离真凶很远，很难一眼看出。
  SQL 注释里改用无反引号的写法。
- ⚠️ **夹具数据要避开内置种子数据的命名空间 slug** `builtin`：我第一版夹具用了 slug=`builtin` 但 id 不同，
  `seedBuiltinSkills` 的 `INSERT OR IGNORE` 因 slug UNIQUE 冲突被忽略 → 命名空间没建成 →
  外键指向不存在的 ns → **所有技能接口 500**。这个 500 看起来像迁移失败，其实是夹具造错了，
  **差点误判成生产 bug**。排查手法：临时把 handler 的 `catch {}` 改成打印异常，再跑一次定位。
